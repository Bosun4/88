# 足球预测链路恢复设计

用户授权沿原框架恢复运行、升级预测逻辑、梳理模型调用和恢复旧版页面风格。本次在原 Python → JSON → GitHub Pages 架构内完成，不改写历史预测与前向锁档。

## 历史依据

最近十次 Football AI Predict 为 #682–#691。#686–#689 的日志均已逐条核验：Run Predictions 开始后 1–2 秒出现“问财业务拒绝 code=1”，随后因无赛程保护旧文件并退出，尚未进入预测模型；其余六次工作流成功。#690 对应 26/26 有主线预测；#685 为 18/18；#684 为 15/15；#683 为 41/43；#682 为 27/28。#691 在 #86/#87 改版后仅 2/42 有主线，9 批请求中 8 批 HTTP 524。数据源业务拒绝与模型超时是不同故障，改版不能解释所有历史失败。

旧版使用 GPT/Grok 初审、交叉质询、Gemini 终审，另有多层重试和备用裁判。新版把它改为 GPT 六场单轮，移除了其他模型凭证。恢复角色分工，但每场固定最多三次调用，不恢复无限扩展的质询/修复链。

## 预测顺序与预算

1. 采集当前竞彩业务日未开赛比赛，保留所有正确比分与让球报价、各市场变化和真实来源；缺失伤停记为未知。
2. 每场 GPT 做盘口与主线分析、Grok 做反证与风险分析，两者并发；相同证据仅保留一份。
3. Gemini 读取赛前证据和两份有效初审完成终审。一个初审失败允许带缺口终审；两者都失败则弃权，初审结果不得假冒终审。
4. 每场最多三次、每次运行最多 180 次，按整场保留预算，最多两个场次并发、模型总并发不超过四。90 分钟停止新阶段，单请求总超时 180 秒，给发布预留时间；每阶段重新检查开赛时间。无隐式重试与修复调用，流式传输与严格完整 JSON 解析保留。
5. 缓存基于语义证据、阶段、模型与提示版本，忽略重复采集时钟但保留开赛时间、报价时间和来源发布时间；失败同样短期缓存。缓存外仍执行赛前时间核验。
6. 区分完成、部分成功、全部失败；记录每阶段请求和有效场数。全部调用失败时保护线上旧预测并使工作流失败，诊断产物保留。赛后复盘默认只对账，不暗中增加 AI 请求。

## 预测质量

保留主线/反向/平局/高比分路径与各自依据、缺口和触发条件。模型自述来源必须匹配实际输入才进入外部事实闸门。赔率隐含概率与模型概率分别表示；没有真实大小球报价不把不完整总进球盘口拼为可投注大小球。有效模型结果不代表必有 A/B 推荐，也不代表胜率提高。

参考 #86 之前深色终端：深蓝黑底、绿色主线比分、琥珀色风险、概要指标、三模型观点并排。沿用新版筛选和可折叠证据，补充调用流程、完成率与故障状态。手机单列，桌面卡片布局。保留未知概率、历史过期提示和主线/风险独立显示。
